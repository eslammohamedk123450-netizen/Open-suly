# Hermes Agent capability integration plan and status

SULY intends to reuse Hermes Agent as its primary general-purpose agent runtime. This document maps Hermes capabilities to SULY's architecture; it is not a claim that all upstream features are currently enabled.

## Core capabilities to integrate

| Hermes capability | SULY destination | Integration status / boundary |
|---|---|---|
| Agent runtime / turn execution | Primary agent service | Runtime pinned, API disabled, not yet operational in SULY |
| Planning / tool selection | Hermes harness | Pending API and event lifecycle bridge |
| Skill discovery and invocation | Skill adapter / scoped workspace | Pending; skill files must be provenance checked and permission reviewed |
| Skill creation / revision | Versioned skill workspace | Pending; generated skills require review, tests and versioning before promotion |
| Persistent memory | Per-user isolated memory namespace | Pending; memory ownership, retention, deletion/export and isolation policy required |
| Session history and search | Conversation/session bridge | Pending; SULY remains authoritative for identity and tenant access |
| Tool calls | SULY capability registry | Pending; all privileged actions require server-side scopes, allowlists, audit and output caps |
| Delegation / subagents | SULY bounded subagent policy | Pending; concurrency, budget, depth, deadline and scope inheritance restrictions |
| Web search / content extraction | Web specialist tools | Pending; search results are untrusted input, URL and egress policies required |
| Browser automation | Browser Use/Skyvern adapter | Separate browser runtime; not enabled by Hermes bridge |
| Terminal / shell | Disposable execution sandbox | Explicitly blocked until sandbox hardening and egress controls are tested |
| File read/write/edit | Task-scoped workspace | Pending; no host filesystem or secrets mounts |
| MCP servers | SULY MCP broker | Pending; per-server allowlist, auth isolation, tool catalog review and approval gating |
| Provider/model routing | SULY AI gateway policy | Pending provider selection, no credentials configured |
| Multimodal/image tools | Capability-specific adapters | Pending; validate content limits, privacy and provider support |
| TTS/audio | Optional media adapter | Pending; explicit consent, rate/size limits and provider selection |
| Cron/scheduled agents | SULY scheduler/task ledger | Not enabled; upstream cron must not bypass SULY quotas, identity or approvals |
| Messaging/channel integrations | SULY channels | Not enabled; upstream gateway/channel ownership must not replace SULY auth |
| Remote execution backends | Sandbox provider adapter | Pending; only approved ephemeral providers, no credential leakage |
| Run status/events/streaming | Durable task event bridge | SULY-owned per-attempt engine run ledger added; live event streaming and remote Hermes run IDs remain pending |
| Stop/cancel | SULY task cancellation | Worker cancellation event reaches Hermes HTTP bridge; client request is aborted on cancellation/lease loss. Upstream execution termination is not guaranteed without a Hermes run-control API. |
| Retry/recovery/checkpoint | SULY durable DAG | SULY-owned retry and checkpoints; Hermes run mapping/idempotency pending |
| Health and metrics | SULY engine monitor | Pending; readiness must distinguish process health from model/tool capability |

## Required staged activation

1. **Sandbox first:** dedicate non-root container user; read-only root filesystem where compatible; disposable per-task workspace; CPU, memory, process and disk limits; no Docker socket; drop capabilities; no host mounts; network egress allowlist; redact logs. Verify actual upstream configuration and image behavior.
2. **API gate:** API server remains disabled until the exact upstream API/tool configuration is reviewed. A key alone is not sufficient safety.
3. **Run lifecycle bridge:** map SULY task+step+attempt to an idempotent Hermes run. Persist run reference server-side, poll or consume events, request upstream stop when cancellation/lease loss occurs, and bound all waits.
4. **Least-privilege tools:** expose only the initial reviewed toolset. Do not forward approval scopes as prompt text or grant Hermes its own access to SULY database.
5. **Skills and memory:** isolated per-user/project, with provenance, safe promotion, retention and delete/export semantics. Skills generated by an agent cannot silently self-grant permissions.
6. **Subagents:** maximum depth/concurrency, shared total token/time budget, allowlisted tools, no ambient identity or secret inheritance.
7. **Specialists:** add code and browser engines separately; Hermes may route but SULY authorizes and leases each specialist task.
8. **Verification:** adapter contract tests, API integration mocks, cancellation/lease-loss tests, sandbox smoke test, security/dependency/license scan, then optional real provider smoke test after user approval.

## Current verified implementation

- Upstream Hermes is pinned to commit `2de9f51b8008a7d49a49221c184f2f11cbfc4af1`.
- Compose profile is opt-in, no host port, and API server disabled.
- SULY bridge settings and a bounded asynchronous HTTP chat bridge exist. A lease-guarded engine run ledger records Hermes attempt start and terminal status without storing prompts, outputs, or credentials. Base URL parsing rejects non-HTTP(S), missing-host, embedded credentials, query strings, and fragments before requests; invalid settings are covered by new tests. The worker now registers `hermes.agent.turn` as an approval-gated task operation (`agent.hermes.run`) with strict input-field and input/output size limits. The operation reaches the bridge only after the worker loads persisted approval scopes.
- Worker `run_once` accepts optional cancel-aware handlers. Lease loss/failure sets cancellation event and prevents result checkpoint. The cancellation event now flows through the approved tool context and engine adapter to abort the in-flight HTTP request; engine timeout overrides are passed through to HTTPX.
- WorkerRuntime forwards the optional cancellation-aware handler interface.
- Unit tests cover HTTP request cancellation, timeout override, approval-preserving event propagation, worker lease heartbeat, and no-checkpoint-after-lease-loss. CI status is tracked per commit; do not treat authored tests as executed until the corresponding GitHub Actions run completes.
- No Hermes container is built or started, no provider/model configured, and no real tool/agent execution is verified.

## Capability enablement policy

A capability is considered integrated only after code exists, required permissions are enforced, tests are run, and its intended runtime is actually started and verified. Documentation or upstream capability descriptions alone do not qualify as integration.

## Tool catalog API

Authenticated clients can now query `GET /v1/tools/approvals/catalog` to discover the currently registered worker operations. The response includes each tool's name, description, permission scope, approval requirement, and `approved` flag for the requesting user's active grants. This endpoint is descriptive only; it does not execute tools or grant/revoke permissions. Hermes remains disabled unless separately configured and sandbox-reviewed.

## Tool schema discovery

The authenticated tool catalog now publishes each registered tool's allowed and required input field names and the registry-enforced maximum serialized input/output byte sizes. This is metadata only: it does not relax the worker allow-list, change approval requirements, or expose arbitrary execution. Client-side forms can use this metadata for discovery while the server remains authoritative for validation.


## 2026-11-20 cancellation bridge update

- HermesAgentAdapter receives the worker cancellation event and the engine-registry timeout.
- ToolExecutionContext carries a server-created cancellation event separately from user-controlled task input and approval scopes.
- Only tools explicitly marked supports_cancellation receive the event; the Hermes operation is marked as cancellation-aware.
- The HTTP bridge uses httpx.AsyncClient and cancels its local request task when SULY signals cancellation. This closes the client-side request and prevents SULY from accepting/checkpointing a late result.
- IMPORTANT LIMITATION: aborting the HTTP request does not prove that a remote Hermes process stopped generating or executing. A future upstream run-ID/stop endpoint is required for authoritative remote cancellation and durable run reconciliation.
- No Hermes API server, provider, worker, or paid service was enabled by this change. Sandbox review remains a prerequisite.


## Durable engine attempt ledger (migration pending)

- `engine_runs` records one row per task-step attempt, keyed by `(step_id, attempt_count)`, with engine ID, status, and timestamps only. It intentionally stores no prompts, model output, access tokens, or provider credentials.
- `start_engine_run` requires the active step lease token, an unexpired lease, and a task that has not requested cancellation.
- `finish_engine_run` accepts only succeeded/failed/cancelled terminal states and requires the same unexpired lease token. A cancellation-requested task forces the run status to cancelled.
- Authenticated users have owner-scoped read access only; writes and RPC execution are service-role-only.
- The migration `20261120153000_engine_run_ledger.sql` is committed but has NOT been applied to the live Supabase project. Hermes remains disabled, so no live execution depends on this schema yet.
- This is a SULY-side attempt ledger, not an upstream Hermes run ID or event stream. Remote cancellation and recovery of an in-flight remote process remain unsupported until Hermes exposes a reviewed run-control API.

## Upstream source and run-control audit (2026-11-20)

- The current immutable source pin used by `engines/hermes/compose.yaml` and `engines/hermes/README.md` is `2de9f51b8008a7d49a49221c184f2f11cbfc4af1`. The earlier pin `9f47677483d1b4de4d1a88d37b3b7ca18b18b215` was also a valid upstream commit; it has been superseded by this newer audited revision. The exact current revision's `LICENSE` is MIT.
- The exact revision includes the native Runs API implementation in `gateway/platforms/api_server_runs.py`: `POST /v1/runs` admits a run and returns a run ID; `GET /v1/runs/{run_id}` provides status; `GET /v1/runs/{run_id}/events` streams SSE lifecycle events; `POST /v1/runs/{run_id}/stop` requests interruption. The API supports `Idempotency-Key` with a 24-hour retention window. This is the preferred future adapter contract over the current one-shot Chat Completions bridge.
- Upstream stop is cooperative: the endpoint initially returns `stopping`; the run settles as `cancelled` after executor-backed work exits. SULY must treat a stop acknowledgement as a request, not proof that the process has already stopped.
- The upstream API server exposes the full Hermes toolset, including terminal commands. It requires a strong `API_SERVER_KEY` (minimum 16 characters) even on loopback. The SULY Compose profile keeps `API_SERVER_ENABLED=false`, supplies no API key, publishes no host port, and remains opt-in.
- Upstream `SECURITY.md` describes Hermes as a single-tenant personal agent and states that the operating system is the security boundary against adversarial model output. For untrusted inputs and shared/production deployments, it recommends whole-process wrapping. Therefore one shared Hermes process must NOT be used as a multi-tenant security boundary. Before activation, SULY needs per-user or per-task process/container isolation, task-scoped storage, resource limits, no host mounts/socket, and default-deny egress through a reviewed proxy/allowlist.
- The exact pinned `pyproject.toml` declares Python `>=3.11,<3.15`, while its current core runtime dependency markers target Python 3.14. Keep using the upstream Dockerfile/runtime rather than importing the full Hermes package into SULY's Python 3.12 API image.
- The current Compose profile is only an isolated development scaffold, not a production sandbox: it has a dedicated named data volume and private Docker bridge with no published port, but network egress and CPU/memory/process limits are not yet constrained. Keep it disabled.
- The source audit confirms the Runs API and MIT license at the exact current pinned revision, but does not yet certify the complete transitive dependency/license set, the exact container runtime behavior under SULY policy, or a multi-tenant deployment. No Hermes run endpoint has been enabled or called from SULY.


## Native Hermes Runs API adapter update (2026-11-20)

- Replaced the one-shot Chat Completions bridge with the upstream native Runs API: SULY admits a run using `POST /v1/runs`, polls `GET /v1/runs/{run_id}`, and requests cooperative cancellation using `POST /v1/runs/{run_id}/stop`.
- Each attempt uses its SULY engine-run UUID as an upstream `Idempotency-Key`. This prevents an HTTP retry for the same SULY attempt from admitting duplicate Hermes work.
- The opaque upstream `run_id` is persisted to `engine_runs.upstream_run_id` only after a lease-guarded RPC confirms the same active step lease. The new migration `20261120173000_engine_upstream_run_identity.sql` adds the column, uniqueness constraint, and service-role-only RPC.
- The bridge refuses to start unless `HERMES_AGENT_ISOLATION_CONFIRMED=true`. This is an operator attestation guard only; it does not create a sandbox or prove that the configured endpoint is isolated. Keep it false until a per-task runtime manager, task-scoped storage, resource limits, and default-deny egress are implemented and verified.
- The adapter currently polls status; SSE event forwarding and remote-run reconciliation after an SULY process restart remain pending. Upstream stop is cooperative and a stop acknowledgement is not proof that execution has already terminated.
- Both new migrations are committed but have NOT been applied to the live Supabase project. Hermes remains disabled by default and no provider or runtime has been activated.
