# دليل تعليمي: تشغيل Hermes الأصلي من خلال SULY

هذا الدليل يشرح مسار تشغيل مهمة Hermes في SULY. الهدف هو فهم الكود والملفات، وليس تشغيل المحرك تلقائيًا.

## 1. الفكرة العامة

- SULY هو النظام المسؤول عن المستخدمين والمهام والموافقات والملكية.
- Hermes هو محرك خارجي ينفذ دور الوكيل.
- لا نرسل إلى Hermes مفتاح Supabase أو صلاحيات المستخدم أو رموز موافقاته.
- Hermes في المصدر الذي راجعناه مصمم كوكيل شخصي أحادي المستأجر؛ لا يجوز اعتبار عملية Hermes مشتركة حدًا أمنيًا بين مستخدمي SULY.

## 2. الملفات المهمة

| الملف | وظيفته |
|---|---|
| `services/api/app/worker_runtime.py` | يراجع الموافقة، ينشئ سجل المحاولة، ثم يوجه الطلب إلى المحرك |
| `services/api/app/services/engine_registry.py` | يتحقق من اسم المحرك والقدرة والمهلة وحجم الإدخال والإخراج |
| `services/api/app/services/hermes_agent.py` | يتصل بواجهة Hermes Runs API |
| `services/api/app/services/engine_run_store.py` | يحفظ معرف التشغيل الخارجي باستخدام RPC خادمية |
| `supabase/migrations/20261120153000_engine_run_ledger.sql` | ينشئ سجل محاولات المحركات |
| `supabase/migrations/20261120170000_engine_run_reconciliation.sql` | يغلق المحاولة إذا انتهت الخطوة أو فقدت lease |
| `supabase/migrations/20261120173000_engine_upstream_run_identity.sql` | يضيف معرف Hermes الخارجي ويربطه بالـlease |

## 3. تسلسل التشغيل

1. يطالب Worker بخطوة ويحصل على lease token.
2. يتأكد SULY من وجود موافقة المستخدم المخزنة.
3. ينشئ SULY صفًا في `engine_runs`، ويستخدم UUID الخاص به كمفتاح idempotency.
4. يرسل `POST /v1/runs` إلى Hermes.
5. يعيد Hermes معرفًا مثل `run_...`.
6. يحفظ SULY هذا المعرف عبر `attach_engine_upstream_run` بشرط أن lease ما زالت صالحة.
7. يتابع SULY حالة التشغيل عبر `GET /v1/runs/{run_id}`.
8. عند طلب الإلغاء، يرسل SULY `POST /v1/runs/{run_id}/stop` وينتظر حالة نهائية ضمن مهلة محدودة.
9. لا يعتمد SULY النتيجة إلا إذا ظل العامل مالكًا للخطوة واجتاز حفظ النتيجة.

## 4. ما معنى Idempotency؟

هو مفتاح ثابت لنفس محاولة SULY. إذا ضاعت استجابة إنشاء التشغيل وأعاد SULY نفس الطلب بالمفتاح نفسه، يستطيع Hermes إعادة نفس معرف التشغيل بدل بدء تشغيل مكرر. لا نستخدم المفتاح نفسه لمهمة أو محاولة مختلفة.

## 5. ما الذي لا يفعله النظام بعد؟

- لا يوجد حتى الآن مدير يشغل حاوية مستقلة لكل مهمة.
- لا توجد حدود موارد وقيود خروج شبكي مطبقة ومثبتة على Runtime الإنتاج.
- إلغاء Hermes تعاوني؛ طلب الإيقاف لا يثبت أن العملية انتهت لحظيًا.
- متابعة الحالة تعمل بالـpolling؛ بث أحداث SSE لم يتم توصيله إلى واجهة SULY بعد.
- لا توجد مصالحة تلقائية بين معرف Hermes الخارجي وتشغيل بعيد بقي بعد إعادة تشغيل SULY.
- الهجرات الجديدة موجودة في GitHub ولم تُطبق على قاعدة Supabase الحية.

## 6. حاجز الأمان

الإعداد `HERMES_AGENT_ISOLATION_CONFIRMED` يبدأ بقيمة `false`. تغييره إلى `true` مجرد إقرار من مسؤول النشر، وليس إنشاءً للعزل. لا تفعّله حتى يوجد مدير Runtime يضمن عزلًا مستقلًا لكل مهمة، ومجلد عمل خاصًا، وحدود CPU والذاكرة والعمليات، وعدم تركيب ملفات المضيف أو Docker socket، وخروجًا شبكيًا افتراضيه المنع.

## 7. طريقة الدراسة

اقرأ الملفات بالترتيب: `worker_runtime.py` ثم `engine_registry.py` ثم `hermes_agent.py` ثم `engine_run_store.py` ثم ملفات SQL. اربط كل خطوة في التسلسل أعلاه بالدالة التي تنفذها. اختبارات Hermes الموجودة تحاكي HTTP ولا تعني أن خدمة Hermes الحقيقية قد شُغلت.
