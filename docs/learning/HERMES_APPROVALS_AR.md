# شرح موافقات Hermes في SULY

## ما هي الموافقة؟

بعض الأدوات قد تنفذ أثرًا خارج المحادثة، مثل تعديل ملف أو تنفيذ أمر. Hermes يوقف التنفيذ ويرسل حدثًا باسم approval.request حتى يقرر المستخدم.

## ما الذي يستقبله SULY؟

من حدث Hermes لا نحتفظ إلا بـ:
- اسم الحدث.
- رقم التسلسل والتوقيت.
- معرف الطلب المعتم request_id، بعد التحقق من شكله.

لا نحفظ command أو description أو preview أو arguments أو reasoning. هذه المعلومات قد تحتوي على أسرار أو تعليمات أو محتوى خاص، ولذلك لا تدخل سجل الأحداث الدائم.

## مسار الموافقة

1. Hermes يرسل approval.request عبر SSE.
2. عميل Hermes يحول الحدث إلى metadata صغيرة.
3. EngineRunStore يرسل metadata إلى RPC.
4. RPC يتأكد من lease الحالي، ومن أن engine run ما زال running.
5. API يعرض طلبات الموافقة المسجلة لصاحب المهمة فقط.
6. المستخدم يختار موافقة لمرة واحدة أو رفض.
7. API يتحقق من أن request_id يخص نفس engine run ولم تتم الإجابة عنه.
8. Hermes يستقبل POST /v1/runs/{run_id}/approval مع request_id والاختيار.
9. SULY يسجل القرار كحدث metadata فقط.

## لماذا لا يوجد زر السماح دائمًا؟

واجهة SULY لا تسمح بـsession أو always أو resolve-all. هذه صلاحيات أوسع من طلب واحد وقد تحول موافقة مؤقتة إلى صلاحية دائمة. لذلك لا نرسل إلى Hermes إلا once أو deny، مع معرف طلب محدد.

## حماية التداخل بين المستخدمين والمهام

- مسار API يطلب task_id وengine_run_id داخليين من SULY.
- الخادم يتحقق من مالك المهمة عبر جلسة المستخدم.
- معرف الموافقة يجب أن يكون موجودًا في سجل الأحداث لنفس engine_run_id.
- لا يقبل الخادم معرف upstream run من العميل.
- فحص lease قبل استدعاء Hermes، ثم RPC يعيد التحقق من lease عند كتابة سجل القرار.
- Hermes نفسه يرفض الطلب إذا لم يعد request_id معلقًا.

## ترحيل قاعدة البيانات

Migration 20261121010000_engine_run_approval_metadata.sql تضيف approval_request_id وapproval_choice إلى سجل الأحداث وتحدث توقيع RPC. القيود NOT VALID لتجنب فشل ترحيل سجلات الموافقات القديمة التي لا تحمل request_id؛ لكنها تفرض على الصفوف الجديدة. لم يتم تطبيق migration على قاعدة حية.

## حدود ما تم إثباته

اختبارات SULY تستخدم HTTP mock ولا تثبت تشغيل Hermes فعليًا. لم يتم بناء runtime أو تفعيله أو توصيل provider. كما لا توجد موافقات حقيقية قيد التشغيل. يجب تطبيق migration في قاعدة disposable/staging وتشغيل integration test مع Hermes معزول قبل التفعيل.

## عرض تفاصيل العملية قبل الموافقة

لا تعرض الواجهة أزرار القرار مباشرة. يضغط المستخدم أولًا على «عرض تفاصيل العملية»، فيطلب التطبيق تفاصيل الطلب نفسه من API. الخادم يتحقق من ملكية المهمة والتشغيل ومن وجود request_id نفسه في سجل الحدث، ثم يطلب حالة Hermes الحالية. يعيد فقط النص الذي جهزه Hermes بعد تنقيح عرض الموافقة، مع حدود للحجم. لا يحفظ SULY command أو description في قاعدة البيانات؛ يعرضهما في استجابة مؤقتة فقط. إذا لم يعد الطلب معلقًا أو لم تتوفر تفاصيل آمنة، لا تظهر أزرار الموافقة والرفض.
